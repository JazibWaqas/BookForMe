# Firestore Seed Scripts

This folder is for maintaining the Firestore demo/dev dataset. Do not run any
script here casually against the live Render project.

## Canonical Database Shape

The current booking system uses these core collections:

- `vendors` - venue/business profile documents.
- `resources` - bookable courts, pitches, or nets owned by a vendor.
- `services` - one active sport/service per vendor, including `sport_type`,
  duration, and pricing.
- `slots` - the single source of truth for availability and bookings.
- `payments` - uploaded payment proof metadata.
- `vendor_payment_accounts` - payment destination details per vendor.
- `conversation_states` - persisted WhatsApp/agent history.

Important: bookings are not stored in a separate `bookings` collection. A slot
document becomes a booking as its `status` changes.

Slot state machine:

```text
available -> locked -> pending -> confirmed -> completed
available -> blocked -> available
locked/pending/confirmed -> available   # cancellation/rejection paths
```

Canonical slot document IDs are generated by `smart_reseed.py`:

```text
YYYYMMDD_HH_vendor_id_resource_id
20260508_18_ace_padel_dha_ace_court_1
```

Avoid old/prototype fields and collections:

- `availability_slots`
- `slot_date`
- vendor-level `service_type`
- generated anonymous vendor IDs from old setup scripts

## Current Safe Path

`smart_reseed.py` is the canonical slot maintenance path. It creates missing
slot documents only and skips any slot document that already exists, regardless
of status. The CLI defaults to a read-only dry run; add `--write` to create
missing slots.

The same function is used by live admin/vendor API endpoints:

- `database.admin_api.admin_generate_slots`
- `database.rest_api.vendor_run_smart_reseed`

This means the CLI script and the app share one slot generation rule.

## Script Inventory

Use intentionally:

- `check_db.py` - read-only status check.
- `verify_slots.py` - read-only timestamp/slot sample check.
- `verify_db_state.py` - read-only structural verification.
- `smart_reseed.py` - additive slot creation only.
- `seed_system_config.py` - writes `system_config/global` only.

Use only for an empty/dev rebuild:

- `seed_all.py` - writes users, vendors, resources, services, payment accounts,
  slots, and sample payments. It should not be used on a live database unless
  you are deliberately rebuilding known demo data.
- `seed_social.py` - writes social/demo collections.

Legacy or dangerous:

- `clear_slots.py` - destructive; deletes every slot document.
- `safe_slot_seed.py` - legacy name is misleading; it deletes all slots before
  reseeding and does not match the current additive workflow.
- `seed_slots_only.py` - legacy wrapper around the old slot generation flow.
- `wipe_firestore.py` - destructive full-project wipe helper.
- `slot_generator.py` - old slot generator used by legacy seed flows. The
  current slot source of truth is `smart_reseed.py`.

## Rule Of Thumb

If the goal is "make sure upcoming slots exist", first run:

```bash
python backend/database/seed/smart_reseed.py
```

Then, only if the dry run looks right, create missing slots with:

```bash
python backend/database/seed/smart_reseed.py --write
```

Use `--days-ahead N` if you intentionally need a longer horizon.

The admin/vendor endpoints call the same `smart_reseed` function directly.

If the goal is "inspect what exists", use a verification script.

If the goal is "reset/delete/rebuild", stop and confirm the target project ID
and reason first.
