## 1. Project Identity

*   **Full Name & Core Purpose:**  
    **BookForMe (JHAT)** is an AI-powered, dual-interface sports booking marketplace that connects customer mobile apps (React Native) and WhatsApp/Web chat users (LangGraph) to sports venue owners via a stateful, transaction-safe reservation ledger.
*   **The Problem & Target Audience:**  
    It solves "informal scheduling and cash-reconciliation chaos" for sports facility operators (futsal, padel, cricket, pickleball) and active sports players in Karachi, Pakistan. It automates 24/7 reservation desks, optimistic slot locking, and mobile wallet bank screenshot auditing.
*   **Live Deployments (Staging/Production):**  
    *   Backend API Service: [https://bookforme-ie34.onrender.com](https://bookforme-ie34.onrender.com)
    *   Interactive Web Chat AI Receptionist: [https://bookforme-ie34.onrender.com/chat/index.html](https://bookforme-ie34.onrender.com/chat/index.html)
*   **GitHub Repository URL:**  
    [https://github.com/JazibWaqas/JHAT](https://github.com/JazibWaqas/JHAT)
*   **Active Project Timeline:**  
    Developed initially as an academic Final Year Project ("Kaavish") in late 2025. Hardened and refactored to production-ready version (v2.1) in **February 2026**, with latest maintenance logs running up to **May 9, 2026**.

## 2. Tech Stack

*   **Backend Layer:** Python 3, FastAPI (async execution), Uvicorn server, Pydantic settings.
*   **Frontend/Mobile Layer:** React Native (TypeScript) running on Expo Go & Expo Application Services (EAS). Key dependencies include `@tanstack/react-query` (v5 caching), `react-hook-form`, `zod`, `axios`, `react-native-calendars`.
*   **AI/ML Layer (Legacy/Current):**
    *   *NLU & Dialogue:* DeepSeek text model (`deepseek-v4-flash`) configured for LangGraph dialogue nodes.
    *   *Vision OCR:* Groq Cloud inference running `meta-llama/llama-4-scout-17b-16e-instruct` to parse banking screenshots.
*   **Database & Storage:**
    *   *Database:* Google Cloud Firestore (NoSQL, transactional database, strict rules schema).
    *   *Asset Storage:* Firebase Storage (bucket `bookforme-c93a6.firebasestorage.app`) for housing raw payment receipts.
*   **API Integrations:** Meta WhatsApp Business API webhook, Firebase Authentication (role management).
*   **Hosting:** Render (`render.yaml` configuration).

## 3. Core Architecture & Data Flow

```
[Customer Chat Turn] ──▶ [FastAPI Webhook / Dev Chat API] ──▶ [LangGraph Agent]
                                                                    │
                                                                    ▼
[Slot locked for 10-min] ◀── [SlotService.lock_slot()] ◀── [Extracts Intent & Slots]
            │
            ▼
[Payment Proof Uploaded] ──▶ [Firebase Storage URL] ──▶ [Vision OCR Service]
                                                                    │
                                                                    ▼
[SlotService.confirm_booking()] ◀─── [Auto-approves lock if amounts match] ◀───┘
```

### Key Services:
*   `WhatsAppAgent` (`backend/whatsapp/agent.py`): Manages message/image routing and session persistence in Firestore.
*   `BookingAgent` (`backend/agent/graph.py`): Stateful LangGraph coordinator that parses intents (GREETING, INQUIRY, INFO_REQUEST, TRANSACTION) and extracts entities (dates, times, sports).
*   `SlotService` (`backend/database/slot_service.py`): High-integrity ledger manager executing **Firestore transaction blocks** to prevent race conditions or double-bookings.
*   `PaymentOCR` (`backend/nlu/ocr.py`): Vision model API caller executing transaction amount extractions.

## 5. Codebase Health & Modularity

*   **Design Pattern:** Modular and clean.
    *   `backend/agent/` isolates the conversational flows.
    *   `backend/database/` isolates schema models and transaction scripts.
    *   `backend/nlu/` isolates intent parsing and visual text extraction.
    *   `App/app/` utilizes the standard Expo file-based router framework (separating user discovery, customer profiles, and vendor calendar dashboards).
*   **Containerization:** Fully supported. Root `Dockerfile` and `Procfile` are present and production-configured.
*   **Security Posture:** Clean. The repository reads API keys and operational secrets strictly via `os.environ` settings defined in `backend/app/config.py`. No credentials are hardcoded.

## 6. How to Evaluate This Repo for Future Hackathons

When deciding whether to build on this repository or start from scratch for a new hackathon, evaluate these key elements:

### 1. Build on top of this repo if:
*   **The Hackathon requires transaction-safety or booking ledgers:** The Firestore OCC transaction framework in `slot_service.py` is exceptionally difficult to rebuild from scratch under a time crunch. Use it as-is.
*   **The Hackathon is "AI-Native Operations" or "Agentic Workflows":** You already have a full LangGraph state machine structure with active slot-locking integrations and automated vision audit loops.
*   **The target is an SMB Service or Marketplace:** The multi-role Expo mobile app, complete with a vendor calendar dashboard, analytics KPIs, and customer discovery screens, saves months of frontend UI configuration.

### 2. Start from scratch (or strip major parts) if:
*   **The Hackathon is strictly web-based with no mobile requirements:** The frontend is deeply coupled to Expo/React Native TSX structures. Writing a desktop Web app would require building a new frontend from scratch, though the FastAPI backend API is fully reusable.
*   **The DB requirement is strictly Relational (SQL):** Firestore is deeply integrated into every service module. Migrating the transactional engine to PostgreSQL or MySQL would require a complete rewrite of the transaction logic.

## 7. Migration & Adaptation Blueprints

### A. Migrating to Google Gemini API
1.  **File to modify:** `backend/nlu/ocr.py` and `backend/agent/nodes.py`.
2.  **Steps:**
    *   Swap `openai` imports with `google-generativeai`.
    *   Configure `google.generativeai.configure(api_key=settings.GEMINI_API_KEY)`.
    *   Change the vision model identifier to `gemini-2.0-flash`.
    *   Pass transaction images as raw bytes to the Gemini model using standard Gemini API image formats.

### B. Migrating to MongoDB Atlas
1.  **File to modify:** `backend/database/slot_service.py` and `backend/app/firestore.py`.
2.  **Steps:**
    *   Configure PyMongo client setups inside database hooks.
    *   Rewrite `lock_slot` and `confirm_booking` database interactions using standard MongoDB session blocks: `with client.start_session() as session: with session.start_transaction():`. This ensures MongoDB Atlas keeps the same zero-double-booking transactional guarantees.

### C. Integrating with the UiPath Automation Platform (AgentHack Track)
1.  **Workflow Hook:** Wrap the FastAPI booking triggers with **UiPath Integration Service** triggers.
2.  **Dynamic Case Orchestration:** Model the slot lifecycle (`available -> locked -> pending -> confirmed`) inside **UiPath Maestro Case** as stages.
3.  **Human-in-the-Loop Setup:** If the visual transaction OCR confidence score falls below `0.90`, suspend the Maestro case and route a task to **UiPath Action Center** for human vendor validation, resuming automated confirmation triggers only after approval.
