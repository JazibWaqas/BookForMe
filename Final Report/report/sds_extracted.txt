Key Challenges
1. Online and oﬄine elements in application
Ideally, most application features and modules should run without being con-
nected to the internet, but keeping everything oﬄine would mean application
size can become huge.
Similarly, keeping application features and modules
available to use only when connected to internet, not only limits accessibility
but Amazon Web Services free tier provides limited access only. Therefore,
deciding which elements to keep online and oﬄine will be a challenge.
2. User experiences on diﬀerent devices
We aim that the the application should be able to run smoothly on most touch-
screen systems. However, diﬀerent systems have diﬀerent touch sensitivities
(touch sampling rate). Moreover, diﬀerent devices have diﬀerent refresh rates
1 which means that user experience may vary depending upon the device being

2.2
Analysis of Hand-drawn Sketches
The drawing module of our application displays a simple sketch to the user and the
user is required to draw the sketch on the canvas using a pen. The main task under
this module is to be able to recognize how good or bad a user-drawn sketch is in com-
parison to the reference image. There exists a generous amount of research within
machine learning approaches that target hand-drawn sketches. Hand-drawn sketches
come with their own share of domain-speciﬁc challenges and beneﬁts as compared
to natural photos. For instance, freehand sketches are highly diverse, sparse, and
abstract and do not follow a speciﬁc set of rules. At the same time, hand-drawn
sketches do not have any background clutter and the sequential nature of sketch
generation allows for better analysis. Sketch properties also allow for various repre-
sentations of hand-drawn sketches and at the same time call for Machine learning
strategies that are speciﬁc to Freehand drawing leading to Sketch-speciﬁc models
that can extract sketch properties and are designed to overcome challenges within
the domain. In this part of the research, we will analyze some techniques that have
been used for sketch recognition, classiﬁcation, and representation.
As compared to natural photos that are pixel perfect, hand sketches are highly ab-
stract. A major challenge in coming up with a representation of free-hand sketches to
model sketch inputs is to look out for richer representations that are based on eﬃcient
storage and at the same time allow for faster calculations. Some popular techniques
for sketch representation include storing freehand sketches as a sparse matrix or in
the form of strokes or pen coordinates represented in Euclidean space. This represen-
tation is particularly useful when considering sketches as time series. Sketches may
also be represented as Static pixel space if they’re being rendered as images. Topo-
logically, freehand sketches can also be stored as connected graphs where each stroke
may be represented in the form of an edge. Such a representation would also comple-
ment the abstract nature of sketches themselves and is expected to be more ﬂexible
as compared to the others. Among various other state of art architectures [15] pro-
posed a “SketchRNN” which is a Recurrent neural network-based deep Variational
AutoEncoder (VAE) capable of generating sketches in a stroke by stroke manner.
This sequence-to-sequence variational encoder has inspired various researchers to
use stroke sequences as input to many recent developments in sketch-based models.
Due to the eﬃciency of the stroke-based representation, our application also aims
to store user sketches in the form of strokes represented by horizontal and vertical
coordinates with respect to time. Figure 2.3 below shows a similar representation of
sketches in the QuickDraw dataset.

to employ online sketch classiﬁcation models to be able to provide real-time feedback
to the user. A sketch recognition network proposed by [12] utilizes the sequential
process of sketching for training and plots each training sketch as a continuous se-
quence of cumulative stroke pictures. Then the deep features extracted from the
corresponding AlexNet [18] are preprocessed and sent into a Gated Recurrent Unit
(GRU) [23] network in sequence. This network generally works for oﬄine methods
but has also proved to work well in online recognition mode due to the involvement of
the intermediate status of the sketches. [14] discusses traditional Machine learning
approaches- including KNN, RNN, SVM, and MLP to recognize hand-drawn im-
ages and is particularly focuses on basic shapes like squares, triangle, and oval. [14]
gives a performance analysis of traditional techniques as compared to deep learning
methods including CNN, LSTM, and WaveNet networks where deep learning models
outperform the traditional approaches alongside ensuring computational eﬃciency.
For automated scoring, [30] proposed Deep convolutional neural networks or Con-
vNets called DeepSketch that uses a modiﬁed structure of AlexNet. The architecture
in [30] is speciﬁcally designed to extract features from diﬀerent layers of DNN which
leaves room for diﬀerent facets of similarity. Similarly, [19] employs a deep learn-
ing methodology that processes two sketch patches together to generate a similarity
score through a semi Siamese network.
Our literature review indicates limited research in the scoring of sketches represented
as strokes and a lack of automatic scoring for drawing in general.

AttemptedExercise and Scorer
• As the name suggests, the AttemptedExercise class is responsible for recording
and saving the user’s attempt. It will also evaluate the exercise by triggering
the scoring methods of the scorer class depending on the module which that
particular exercise belongs to.
• The Scorer exercise is responsible for evaluating the exercise and generating
a score that is to be saved and sent back to the user as feedback. The class
contains four sub-classes, each corresponding to the four diﬀerent modules of
our application. Each module has a distinct method for scoring the exercise,
with separate models using which the combined is generated. The logic for
generating the ﬁnal score is implemented in the virtual function getScore().
Dashboard
• This is a static class which is responsible for the operations that would be
required when displaying the feedback and performance of a child to their par-
ents. This includes, but is not limited to, generating reports and corresponding
graphs for each child.

2.4
Natural Language Generation Through Deep
Learning Models
Before transformers and attention mechanisms were common for natural language
generation, state-of-the-art architectures such as Recurrent Neural Network (RNN)
and Long Short-Term Memory (LSTM) were used for this task [22]. However, one
of the main problems with these models was the vanishing gradient problem due to
their deep architecture. Transformer-based language models marked a new era of ad-
vancements in natural language generation tasks. The GPT-2 [47] model, a 1.5 billion
parameter transformer, was introduced in an effort to perform unsupervised learning
for natural language processing tasks such as question answering, machine transla-
tion, reading comprehension, and summarization. It was trained on a dataset of 8
million web pages. Following this, many models based on GPT-2 were introduced.
DLGNet [43], a transformer-based model is an extension of GPT-2 for multi-turn di-
alogue modelling. It proposes a hybrid of long-range transformer design and random
informative padding injection.
Currently, there exist several pre-trained models for open-ended conversational
agents. Meena [3], uses social media comments to perform pre-training for dialogue
generation. Its neural network with 2.6 billion parameters has been trained to reduce
the perplexity of every next token. Blender [54] suggests fine-tuning the pre-trained
dialogue model with human-annotated datasets in order to emphasize the conversa-
tional traits of engagingness, knowledge, empathy, and personality.
While much work on natural language generation is being done in prominent
languages such as English, many resource-poor languages including Urdu have been
left behind due to the lack of relevant resources. There have been instances of work
being done on dataset compilation and natural language generation in languages
other than English [39, 23, 2, 17, 5]. However, to our knowledge, no such effort has
been made in the Urdu language.

Data Pipeline
Data Pipeline for Chatbot Framework (RASA)
The input to the data pipeline is the Urdu text converted from the user input audio.
RASA framework breaks down the processing of user query and returning of response
into two components. The text input is first passed through the NLU component
of the framework which involves natural language processing over the raw text and
outputs intents and entities. There are two parts of the NLU component, 1) Urdu
NLP Pipeline and 2) Entities Extractor and Intent Classifier. The raw Urdu text is
first passed into the NLP pipeline which outputs processed query. This processed
query is then passed into the intent classifier and entity extractor, which maps it to
a pre-defined intent and extracts important entities from it. These extracted intents
and entities are then passed on to the second component of the framework called
RASA core. RASA core uses a classifier which finds out the best response to the
query and outputs the response, which is then sent to the user. Table 4.3 shows the
complete data-pipeline for our chatbot module.
